## 0. 先回答一个被直接提出的问题：子包能解决文件尺寸的墙吗？

**不能。** 三条实测证据：

| # | 证据 | 含义 |
|---|---|---|
| 1 | 棘轮 scope = `src` + `tests` + `packages` + `scripts`；而 **`packages/` 超限文件数 = 0** | 300 行上限**在子包里同样生效**。搬到子包不是逃生舱 |
| 2 | rid-016 是**把代码从 `packages/*/src` 挪进 `src/services/*`**，不是新建代码 | 一个 1200 行的文件**住在哪儿都超限**；census 不因搬家而变 |
| 3 | 新文件在 300 行以内 → **不产生 excess** | **新代码的成本本来就是 0** |

> **结论：那堵墙是「编辑形状」的，不是「增长形状」的。** 真正被卡住的是**修改那 163 个已超限文件**（本次 slice 为了给 adapter 加 2 行，不得不先做一次等价搬迁）。
>
> 子包解决的是 **npm 产物边界**（rid-016 维护税那条），与文件长度**是两条互不相干的政策**。

### 1.3 强制链的既有洞（本 slice 刻意未修）

`gate enforce` 的 `classifyTool` 只认 `Bash`/`Agent`/`Task`/`EnterWorktree`/`Workflow`，**其余一律落到 `'Other'` → 短路放行**。
→ **今天任何非 Bash 工具（含 Write/Edit/所有第三方 MCP server）都在强制链之外。** 面比 MCP 那刀大两个数量级，值得单独论证。

### 1.4 工具缺陷（用出来的）

| 缺陷 | 实测 |
|---|---|
| `peaks audit goal` 输出在约 **3.6 KB 处截断** | 两次 `INCOMPLETE_AUDIT: Unterminated`，换极短 need 才成功。**它撑不到 spec 规模的输入**，而它自称要"让人一次读完" |
| `peaks` 的 `.cmd` shim **吃不下含换行的参数** | `InvalidBatchScriptArg`。双引号无害，**换行是唯一触发条件** |
| `TYPE_SANITY_VIOLATION` 是时序门 | PRD `handed-off` **在代码落笔前不可能通过**（比对的是当前 diff）。`--allow-incomplete` 不覆盖 |

### 1.5 本次交付留下的边界（**未验证，非瑕疵**）

- **端到端 MCP 注册**：本机无 MCP client 可加载 server；跑 `peaks mcp install` 会**改用户真实 user-scope 配置**，故未跑
- **L3 端到端**：`peaks` 在 PATH 上是**已安装构建而非工作树**，故拦截器改动无法在本机端到端验证
- **C 层沙箱**：CI-only，**从未实跑**

### 3.6 「改政策」的精确对象（**已论证**）

`fileSizeOverCap`（文件数）与 `fileSizeExcessLines`（超出行数）**各自独立棘轮**，而单调守卫的规则是「**任一 key 高于基线即拒**」。实测推演：

```
src/cli/commands/loop-eval-commands.ts = 1125 行 (cap 300，超 825)
  拆 2 份 → 563 行/份 → 两份仍 >300 → overCap 1→2   ✗ 拒
  拆 3 份 → 375 行/份 → 三份仍 >300 → overCap 1→3   ✗ 拒
  拆 4 份 → 282 行/份 → 全部 <300   → overCap 1→0   ✓ 允
```

→ **一个把 825 行超额降下来的改动，会因"超限文件数"上涨被挡。** 这**不是硬阻塞**（拆得够深即可，本次 slice 就是如此），但它把拆分变成**必须一次做全**。

**联合判定**：`overCap` 允许上涨，**仅当同一次变更中 `excess` 确实下降**；双升则拒。

> 这是对**安全机制**的修改，必须**单独立项**——不得在还债 slice 里顺手改。

## 5. 补记（同日）：本规划里**两条结论被推翻**

### 5.1 §1.3「强制链的既有洞」—— 不成立

原文把 `gate enforce` 对非 Bash 工具的 fail-open 称为"面比 MCP 那刀大两个数量级"的洞。观察对，
**推论错**：`enforceBashCommand` 收的是 shell 命令字符串，`Write`/`Edit` **没有可评的东西**；
worktree 腿是刻意的 tool opt-in；MCP 那条 fail-closed 分支被刻意放在最前，注释写明了原因。
它是**范围问题**（该不该管 Write/Edit），不是缺陷。经用户决定：**不做**。

### 5.2 §2 的 W1a/W1b —— 收益口径只对 `src/` 成立

实测：`scripts/**` 与 `tests/**` 属 `shadow.scopeDirs`，**不受任何 file-size ceiling 约束**。
拆它们移动的是 census 与 shadow 块，**不是 ceiling**（rid-043 前后 gated 均为 `117 / 32979`）。
所以 §2 里把 W1b（命令层）与 `scripts/` 并列成"两笔债"是不准确的：只有 `src/**` 那部分会动棘轮。
