# 对「数量」打棘轮，看不见「替换」

## 事实（2026-10-09，rid-038 的 format-check 棘轮，QA 独立发现）

第一版 CI 棘轮断言 `unformattedCount <= BASELINE (12)`，成功时打印：

```
format-check-ratchet: held — at the baseline, no new unformatted file.
```

**QA 指出这个判据有个洞**：**修掉一个旧的未格式化文件 + 新增一个未格式化的 → 计数仍是 12 → 仍绿**，而那句文案声称 `no new unformatted file`——**在那种情形下是假的**。

而这个 slice 的**整个宗旨**就是消灭"长得像通过"的检查。**它自己种了一个。**

## 修法：判据从数量改成**集合包含**

基线里的 **12 个文件名**就是允许集；判据 = **当前集合 ⊆ 允许集**。

- 修掉一个旧的 → 集合变小 → 仍绿（正确）
- 新增一个 → **不在集合里** → **红且点名**（正确）
- 允许集**只许缩小**，不得增补

方案落地后，把**原来的计数形判据注入回去**作为测试臂：`3 failed | 3 passed`，**arm C 红**——即**缺陷被机械捕获**。

## Why

`count` 是 `set` 的**粗粒度投影**，而**投影不是单射**：多个不同的集合映射到同一个计数。任何**基于计数的棘轮**都无法区分"变好了"与"换了一个"。

**更糟的是文案**：基于计数的门只能说出关于计数的真话。一旦它把计数的不变说成集合的不变（"no new X"），**它就在用真数字说假句子**——这比单纯的漏检更难发现，因为数字是对的。

## How to apply

- 打棘轮时，**先在集合上打，再考虑是否需要在数量上打**。
- 若判据是数量，**输出的句子必须只说数量**（"count unchanged"），**不得**升级成集合断言（"no new X"）。
- 判断"能否因无法失败而通过"时，除了注入"让计数升高"，**还要注入"替换"**——这是计数盲区，注入升高测不出来。
