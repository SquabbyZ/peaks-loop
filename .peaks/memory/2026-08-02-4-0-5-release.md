# peaks-loop@4.0.5 — 2026-08-02 (statusline polish + sub-agent merge bundle)

## What shipped

Two coordinated slices and three business-risk resolutions are now on npm as
`peaks-loop@4.0.5`. The release is the first successful 4.0.x GA to
`dist-tags.latest` since the 4.0.3 GA on 2026-07-30 (the 4.0.4 attempt
failed for the same reason 4.0.5 first failed; see below).

### 1. `2026-08-01-statusline-auto-compact-progress` (RID 1)

- primary Claude Code statusline polish: cyan brand RGB `#5A65D8`,
  peaks-code mode display scoped to the active peaks-code session, `→`
  connector, `empty` idle label, 2.4s breathing pulse.
- terminal statusline now always surfaces both layers: orchestrator
  (1-level) and bee (1-level sub-role). When the active skill is a
  bee (e.g. `peaks-rd`), the line reads
  `Peaks ● peaks-rd ↑peaks-code [full-auto] → peaks-loop`.
- slow-blink idle glyph: the `○` is wrapped in the ANSI slow-blink
  SGR (`\x1b[5m`) for `ansi-unicode` and `unicode` capabilities, so
  the line reads as a pulse on terminals that honor the SGR. `ascii`
  capability stays plain to keep file / log consumers clean.

### 2. `2026-08-01-subagent-merge-and-e2e` (RID 2)

- sub-agent dispatch governance: parent session auto-merges the
  agent branch back to the caller's working branch
  (`--ff-only` on `main`, `--no-ff` on a feature branch).
- Playwright MCP browser sessions are isolated by per-dispatch
  Chromium profile (no extra LLM cost; user-data-dir and
  profile-name stamped as env vars by the dispatch CLI).
- long-lived local services are killed before merge-back via
  `peaks sub-agent shutdown register`; the registration file is
  `.peaks/_runtime/<sessionId>/dispatch/<dispatchId>/service-registrations.json`.
- merge conflicts re-dispatch the same sub-agent with an enriched
  prompt (original task + transcript + conflict diff). Bounded to
  one re-attempt; a second conflict escalates.
- a single end-to-end Playwright verification runs after merge
  (`peaks e2e verify --slice <rid>`). The real runner spawns Chromium
  with the per-dispatch flags; deterministic stub fallback when
  either env var is unset (CI smoke).

### 3. Schema v3.2 silent-upgrade

- `DispatchRecord` v3.2 adds two optional fields: `serviceKill:
  ReadonlyArray<...>` and `mergeBackAttempts: number`. v3.1 records
  on disk are upgraded transparently on read; the unit test
  `dispatch-record-writer.test.ts` covers the backfill.

## Release mechanics — what made 4.0.5 finally ship

The 4.0.4 attempt on 2026-07-31 failed silently and the 4.0.5
first attempt (commit `3700bcc`) failed at the same step: the npm
publish of `peaks-loop-shared@0.0.33` was rejected because 0.0.33
was already on the registry (from a manual run during the
tombstone-resolution slice). The `Idempotency guard: skip bump when
local root version already equals dist-tags.latest` step only
checks the **root** package, not the sub-packages. Fix for 4.0.5:
manually bump the 3 conflicting sub-packages past their
registry-pinned versions:

| package                        | local | registry pinned | bumped to |
| ------------------------------ | ----- | --------------- | ---------- |
| `peaks-loop-shared`            | 0.0.32 | 0.0.33         | 0.0.34     |
| `peaks-loop-mut`                | 0.1.6  | 0.1.7          | 0.1.8      |
| `peaks-loop-shared-channel`    | 0.0.11 | 0.0.12         | 0.0.13     |

After amend on `main` and `git push origin v4.0.5 --force`,
`publish.yml` Run 113 succeeded in 1m 17s. The `dist-tags.latest`
on npm is now `4.0.5`.

**Follow-up** (separate rid): the `Idempotency guard` step should
check sub-packages against `dist-tags.latest` too, not just the root.
The current 4.0.5 release works around it by always bumping past the
registry version, which is hacky and will fail again next time the
auto-bump script picks a sub-package version that already exists.

## Carried forward

- The `Idempotency guard` step in `publish.yml` should check sub-packages
  against `dist-tags.latest` (separate rid; bumps the publish.yml).
- The Playwright runner is intentionally minimal (navigate + substring/CSS
  matchers). Multi-tab / screenshot / video / `await expect` retry
  logic belong in a follow-up slice.
- The 2-level terminal statusline uses the bee→parent map (12 entries);
  unknown skills (e.g. `peaks-some-bee-future`) render without a parent
  marker — graceful degradation.

## Lessons

- The publish system MUST compare sub-package versions against
  registry before auto-bumping, not just the root. The current
  workaround (manually bumping past the registry version) is a hack
  that will fail again on the next 4.0.x release.
- CHANGELOG entry formatting matters: `awk -v ver=4.0.5` requires the
  pattern `^## 4.0.5 <separator>` where `<separator>` is space,
  `(`, or `—`. A bare `## 4.0.5` heading (no trailing separator)
  fails the gate silently. Always include the date and description
  in the `## <version> — YYYY-MM-DD (description)` form.
- When the host agent tool spawns sub-agent worktrees, the harness
  IS the source of truth for the sub-agent presence; Peaks must
  reconcile the on-disk `.claude/worktrees/agent-*` against its own
  lease store via `peaks worktree reconcile-host`. This was addressed
  earlier in the `2026-08-01-host-worktree-governance-repair` rid;
  the 4.0.5 ship did not regress that.
