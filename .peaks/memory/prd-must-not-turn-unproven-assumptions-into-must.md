# PRD 不得把「待证明的假设」写成 MUST

## 事实（2026-10-09，rid-035 slice ①）

PRD 初稿写了一节：「本段**必须覆盖**的 5 条 argv」。但这一段的**全部意义**就是证明它们只读——**"必须覆盖"是在证明跑之前替证明下结论**。

结果：证明装置如实裁定 `project dashboard` 会 `execFileSync('git',['rev-parse','--show-toplevel'])`、违反只读第 4 条，于是被移出白名单。交付随即"违反"了那条 MUST——**而那条 MUST 本就不该存在**。

QA 明确指出这一点，并把它标为"用户选择题"而非 RD 可自决项。

## Why

PRD 里 MUST / 验收标准的分量很重，会被下游当作硬门。一旦它承载的是**假设**而非**要求**：

- 证明如实推翻假设时，产出的不是"发现了一个事实"，而是"交付不合规"——**叙事被扭曲**。
- 后来者为了满足那条 MUST，会倾向于**放宽证明**而不是接受裁定。这是最坏的方向。

## How to apply

- **候选清单**与**验收要求**必须分节书写：前者是"待裁决的输入"，后者是"必须满足的门"。
- 措辞上：用「候选 / 待验证 / 由 X 裁决」；**不要**用「必须覆盖 / 必须通过」去描述尚未证明的东西。
- 若一条 AC 依赖某个尚未运行的证明，AC 应写成**关于证明本身**的要求（如「每条候选 argv 逐一接受证明裁决，未通过者被排除并记录理由」），而不是**关于证明结果**的断言。
- 交付被证明推翻时，正确动作是**记录并解释**，不是调低证明的严格度。相关：[[proof-gated-by-skipif-can-vanish-and-report-success]]。
